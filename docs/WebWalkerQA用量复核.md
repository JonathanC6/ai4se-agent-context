# WebWalkerQA 的 token 去了哪里？

把同一批 20 题的实际请求按可见输入重新计算后，**独立 PACE-v2 比同轮 ReAct 多送入约 57.3 万 token。动作调用占增量的 49.3%，历史摘要占 31.1%，Glimpse 调用为 0。** 较早的标准 PACE 的同轮结果也值得区分。它多送入约 48.5 万，摘要占 47.7%，是最大的单项。

## 网关回报为什么可疑？

格式重试提供了一个天然对照。第一次回复的格式不合格时，程序保留同一步的问题和全部历史，只给系统提示增加 80 个字符，再请求同一模型。下面两对都来自最终采用的轨迹。

| 题目与决策步 | 本地输入估值，首次 → 重试 | 网关输入回报，首次 → 重试 | 首次回报的缓存读取 / 写入 |
|---|---:|---:|---:|
| ReAct 第 407 题，第 1 步 | 981 → 1,000 | 291,296 → 382 | 283,290 / 7,996 |
| PACE-v2 第 47 题，第 2 步 | 2,666 → 2,686 | 218,780 → 2,213 | 212,974 / 5,798 |

本轮共有 114 对这样的格式重试，其中 58 对的网关输入相差超过 10,000。ReAct 和 v2 的全部动作请求分别有 97.8%、96.1% 的网关输入被标为缓存读取或写入。第 407 题还说明直接扣除两个缓存字段会低估输入。该题首步相减只剩 10，用户和系统实际发出了 1,325 个字符。

逐题、逐角色核对后，四组最终采用的轨迹中，每条已记录响应都满足“网关输入 + 网关输出 = 网关总量”。程序每条只加一次总量，缓存分项未再加总。本轮两组 349 条动作响应各有独立的响应 ID。相邻请求的回报可以从 29 万降到几百，也不符合按本次实验单调累计的解释。旧流水中的非动作响应缺少响应 ID，能核验调用数和加总，无法逐条用 ID 排重。

这些记录把异常定位到了**网关返回的输入和缓存字段与客户端可见文本严重不一致**。网关是否在上游加入了额外上下文、怎样生成缓存字段、最终按什么价格扣费，现有客户端记录无法区分。还需要供应方按响应 ID 核查上游请求和扣费明细。

## 用什么数比较两种方法？

每种方法只取形成最终成绩的 20 条轨迹。轨迹中的格式重试、收尾和裁判调用都计入，被整题替换的旧尝试单列在原运行报告。动作请求采用发送时保存的本地估值。网页提取、摘要、规划、复核和裁判，使用归档的源正文、提取窗口、历史块和原函数离线重建输入。复算核对了源正文哈希、重读窗口、每题每个角色的请求数与网关分项。这个过程没有调用模型。

同一把本地尺按消息用固定 BGE 分词器计数，再乘 0.851 逐条取整，每个请求加 646 的固定开销。这是实验预算的统一估值。旧流水没有保存所有模型回复的原文，因此这次能独立重建的是**输入**，输出单列网关回报。Claude 的精确分词和用户的实际账单仍需单独核实。

| 20 题最终轨迹 | 请求数 | 本地可见输入估值 | 网关回报输入 | 网关回报输出 | 网关回报总量 |
|---|---:|---:|---:|---:|---:|
| 本轮 ReAct | 196 | 544,251 | 8,014,838 | 44,610 | 8,059,448 |
| 本轮 PACE-v2 | 462 | 1,117,382 | 13,013,121 | 148,361 | 13,161,482 |
| 历史同轮 ReAct | 159 | 468,702 | 1,171,705 | 73,758 | 1,245,463 |
| 历史标准 PACE | 379 | 953,316 | 2,296,682 | 193,133 | 2,489,815 |

即使去掉每次请求的 646 固定开销，本轮 ReAct 和 PACE-v2 的可见正文折算量仍为 417,635 和 818,930，v2 多 96.1%。此时动作和摘要分别占增量的 57.7% 和 25.8%，顺序相同。两轮的搜索服务、停止条件和动作协议有变化，所以每个 PACE 版本都和各自同轮的 ReAct 比。

## PACE-v2 多花在哪些环节？

| 环节 | ReAct 请求数 / 本地输入 | PACE-v2 请求数 / 本地输入 | v2 的输入增量 | 占全部输入增量 |
|---|---:|---:|---:|---:|
| 动作模型 | 135 / 394,799 | 214 / 677,286 | +282,487 | 49.3% |
| 历史摘要 | 0 / 0 | 116 / 178,520 | +178,520 | 31.1% |
| 检查草稿、核验补证 | 0 / 0 | 32 / 46,989 | +46,989 | 8.2% |
| 网页提取，含重读原网页 | 46 / 135,481 | 60 / 179,004 | +43,523 | 7.6% |
| 初始事实清单 | 0 / 0 | 20 / 14,783 | +14,783 | 2.6% |
| 裁判 | 15 / 13,971 | 20 / 20,800 | +6,829 | 1.2% |
| **合计** | **196 / 544,251** | **462 / 1,117,382** | **+573,131** | **100%** |

**动作模型主要多在调用次数。** 平均每次可见输入从 2,924 增至 3,165，增加约 8%。动作请求却多了 79 次，其中 44 次是额外决策步，35 次是额外的格式重试或收尾。两组重试与收尾的输入分别为 122,124 和 239,292，相差 117,168，已计入动作行。缩短单步上下文可以容纳更长的轨迹，但每多走一步，当前可见的历史就会再发送一次。

**摘要确实有成本。** v2 为 116 个工具观察各生成一次摘要，请求输入合计 178,520。网关还回报这 116 次生成了 58,764 个输出 token，摘要也是输出侧的重要来源。按网关原始总量分摊，摘要占 v2 增量的 59.3%。即使两边都只看输入，网关口径仍给出 59.4%（2,966,748 / 4,998,283），客户端可见输入则为 31.1%。

**Glimpse 没有贡献这轮增量。** 两组都没有执行过 Glimpse。v2 实际做了 12 次 Reread，ReAct 做了 3 次。Reread 会重新把已保存的网页片段交给提取模型，相关输入归入“网页提取”。12 次里有 11 次出自提交前的自动补证。检查草稿的 32 次请求另计在“检查草稿、核验补证”。

## 标准 PACE 的情况有所不同

历史标准 PACE 比其同轮 ReAct 多了 484,614 个可见输入 token。摘要占 231,245（47.7%），动作占 177,236（36.6%），网页提取占 68,392（14.1%），裁判占 7,741（1.6%）。标准 PACE 为 135 个历史块生成摘要，实际 Glimpse 同样为 0。它平均每次动作输入约 2,984，略低于同轮 ReAct 的 3,028。动作请求从 106 次增至 167 次。因而该版本确实应关注摘要成本，也应保留对“压缩后还能继续走多少步”的衡量。

## 后续怎么记

公共请求记录器现在对动作、网页、摘要、规划、复核、裁判统一记录请求哈希、响应 ID、缓存分项、客户端输入子词数、本地预算估值和可见输出子词数。原始网关用量继续保留。输出只数响应中实际可见的文本，不推算隐藏推理或服务端模板。字段缺失会标注覆盖数。可见输出子词数也可用于后续区分“摘要输入长”和“摘要写得长”。

从仓库根目录可以在已有实验归档上离线复算表中数字。需要本地分词器及按哈希保存的网页正文。

```sh
PYTHONPATH=PACE-v2/src:PACE/src:PACE PACE/.venv/bin/python -m pace_v2.token_audit
```
